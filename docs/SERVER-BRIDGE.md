# Dedicated-server bridge configuration

This preview supports one designated **guild text channel** through official Discord Bot REST v10. It polls new human messages and sends messages/files with a bot account. It does not automate personal accounts and does not implement Gateway, DMs, threads or Discord feature parity.

## Explicit server-side opt-in

Live mode requires all of the following, supplied by the operator only after approving the bot setup and test channel:

| Setting | Purpose |
| --- | --- |
| JVM `-Ddiscraft.discord.enabled=true` | Explicit live-adapter opt-in (contains no secrets) |
| `enabled=true` in server config | Select official Bot REST adapter |
| `channel` in server config | Numeric ID of the designated guild text channel |
| `botToken` in server config | Bot secret, stored only on the dedicated server |
| `allowedPlayers` in server config | Comma-separated authenticated player UUIDs; empty denies players; `*` explicitly permits all players |
| Dedicated server, `online-mode=true` | Bind player identity to authenticated server connections; live mode is refused on integrated/offline servers |

Copy [the empty example](../examples/discraft-server.properties.example) to the dedicated server's `config/discraft-server.properties`, restrict filesystem access to its operator, fill it locally, then restart the server. The file uses UTF-8 Java properties and is limited to 8 KiB; unknown keys, malformed values and symlinks are rejected. Missing config defaults to disabled; invalid config disables the bridge without logging its values or parser exceptions. Empty `channel`/`botToken` placeholders are valid only while disabled. No file containing a real credential is generated by DisCraft or by the tests.

**Production reads this config only.** `discord_token`, `discord_channel` and the old `DISCRAFT_*` variables have no runtime effect. There is no environment fallback. The config is loaded only on an authenticated dedicated server, never by the client. Its secret fields remain in server memory and are never part of packets, status text or config synchronization. Real `discraft-server.properties` files and runtime directories are Git-ignored; CI uploads only named test-evidence directories and the mod JAR, not server configs. Do not add local configs to CI artifacts, backups shared with clients, or bug reports.

Keep the bot token off command lines, client machines, game packets, repository files, screenshots and logs. Do not enable HTTP header/debug logging around live credentials. Startup mode/status describes configuration, not proof of Discord reachability. The separate opt-in multiplayer smoke JVM property selects only the fake adapter and bypasses live config loading; it is a test mechanism, not a production mode.

The approved bot installation needs View Channel, Read Message History, Send Messages and Attach Files for this channel, plus external-emoji permissions where applicable. Reading ordinary guild message content/media through REST also depends on Discord's Message Content access/intent requirements. Upstream permission and authentication failures fail closed; 401/403 become terminal until the operator corrects the setup and restarts. Do not request Administrator merely for this bridge.

Official references: [message API](https://docs.discord.com/developers/resources/message), [Message Content access](https://docs.discord.com/developers/gateway/you-might-not-need-a-privileged-intent), [rate limits](https://docs.discord.com/developers/topics/rate-limits).

## Delivery semantics

- Only the mod composer is forwarded. Sender names and canonical event IDs are generated on the logical server; client-supplied authors/catalogs are rejected. Regular vanilla chat is not forwarded.
- The adapter sends a `<playerName> ` prefix with exactly one separating space and no backslash (for example, `<Aitchn> 你好`), using the authenticated server-derived player name, and empty `allowed_mentions.parse` plus a bounded list of explicitly selected and server-validated Discord user IDs, uses a bounded nonce, and does not automatically retry uncertain sends. Close does not unsend. A disconnect before work starts cancels queued work; an already transmitted request can be uncertain.
- Receiving starts at the current latest channel message, deliberately skipping startup backlog. It polls at most four events per page, suppresses duplicate IDs, ignores bot/webhook messages, preserves its cursor across transient failures, and backs off. Cursor/history/replay state are bounded and in memory; restart is not durable recovery or exactly-once delivery.
- 429 `retry_after` blocks early HTTP retries, conservatively across this adapter. A queue-full, rate-limit, rejected upload or uncertain delivery is reported to the sending client. No network exception body, authorization header or bot token is logged by the adapter.
- Discord static/animated custom markup is resolved through bounded official CDN paths. Outbound custom emoji must be available to the bot in the configured guild catalog; stale names are canonicalized by stable ID, and unknown/deleted/unavailable/restricted IDs are rejected before sending. Inbound channel emoji still use the bounded decoder. There is no arbitrary external GIF provider.

## Automatic server notifications

Native `%item` expansion is separately opt-in with `itemDisplay=true`: see the
[authoritative main-hand snapshot and headless model/font support profile](ITEM-DISPLAY.md).

`notifications=join,quit,death,advancement,lifecycle` explicitly enables categories;
the default is empty, including on existing configurations. Nothing automatically
posts merely because the mod was upgraded or a test server was started. Player
events follow the existing player allowlist; lifecycle notices are server-wide.
All notices use the `Server` author prefix and have no selected mentions. Generated
names/text escape Discord Markdown and neutralize `@` syntax. Overlong generated
text is bounded. Delivery is best effort on the existing 16-job queue: overload,
network failure or an uncertain POST can lose a notice; there is no automatic resend.

Join/quit use login/logout events, not dimension changes or respawns; repeated
login/logout callbacks are suppressed. Death messages use the combat tracker's
semantic component and wait until END tick, checking the event's final cancellation
and dead state; a cancelled death or immediate rescue is suppressed. The same dead
player entity is announced once until respawn/logout (bounded to 128 tracked deaths).
Advancements use the completion event and recheck progress after the event. They
respect `announceAdvancements`, display/announce flags and omit recipes and hidden
advancements. The 4,096-entry per-server-run dedup window sends a completed player/
advancement pair once while retained; revocation/recompletion inside that window
does not generate another notice. Pending deaths/advancements cap at 128 each.

The transport is created at `ServerAboutToStartEvent`. Starting and ready notices
are separate; only `ServerStartedEvent` claims ready. Normal stop admits a final
notice after earlier work and drains within **one eight-second total deadline**,
then interrupts remaining jobs and closes transport. Failed startup cleanup does
not claim ready or normal shutdown. Crash, kill, network loss and power failure
cannot reliably deliver a closing message; no such promise is made.

Discord localization is independent of game clients: see [local resource packs and
component fallback](RESOURCE-PACKS.md). The headless dedicated-server acceptance
uses synthetic Forge events/fake player state and a recording TEST recipient; it
does not contact Discord or prove human gameplay/live notice delivery.

## Guild emoji catalog and native picker

The server resolves the guild from the configured text channel and reads its official [guild emoji list](https://docs.discord.com/developers/resources/emoji#list-guild-emojis) and its own bot member roles. It never accepts a guild ID, role policy, CDN URL or credential from the client. Production continues to read credentials only from server config. Metadata retains stable emoji ID, current name, animation, availability and conservative bot-role eligibility; clients receive only safe metadata and restricted/permitted flags, never role IDs or credentials. A role-restricted emoji is enabled only when the bot has an explicitly matching role; no Administrator exception is assumed.

The upstream list endpoint is not paginated. Each read is body-bounded, rejects more than 2,000 upstream entries, sorts deterministically by name then ID, and publishes at most 512 entries in a 48 KiB metadata packet. A larger valid list is marked incomplete in the picker. Metadata refreshes at most once per minute; version changes invalidate deleted, unavailable or animation-changed preview entries, while a rename retains its ID-keyed image. Permission/authentication failure clears the catalog; clients also expire metadata after two minutes without a valid heartbeat. The shared 429 gate and no-redirect policy apply. Rename/deletion/role updates are observed on the bounded refresh cadence, rather than through Gateway events.

Native chat's **D** category shows synchronized guild emoji with name search, all/static/animated filters, static or animated previews and disabled unavailable/restricted cells. Equal names remain distinct by ID and show an ID suffix. A click rechecks the latest entry by ID, so a stale hit uses the current renamed entry or does nothing after deletion/permission loss/disconnect. Selecting an emoji inserts markup into the composer and does not send automatically. Fixture mode remains explicitly labelled **TEST (not Discord)** and uses bundled fixtures only.

Only visible entries request previews: up to four IDs per batch, at most one batch per client every 1.25 seconds, and one admitted preview job at a time on the server. Requests share the existing packet/byte/queue admission limits. A batch shares the six-second/eight-attempt media deadline and requests fixed official emoji CDN paths at size 32, with no Bot authorization on CDN requests. Server and client caches each cap 64 entries/images, 2 MiB encoded bytes and 2,097,152 decoded pixels; a single preview is limited to 256 KiB and 262,144 decoded pixels. Positive cache TTL is ten minutes; server negative TTL is one minute, client failure/timeout TTL is thirty seconds. Closed pickers stop requesting new previews, and disconnect clears client state. Texture uploads are limited to visible cells and released when no longer visible. Unsupported or oversized previews stay placeholders; metadata eligibility does not promise a successful upstream send.

A read-only, explicitly authorized local harness fetched the actual configured guild catalog and sent it through real dedicated-server metadata/preview packets to Minecraft's native picker. It displayed 55 entries, loaded 52 usable previews, disabled three unavailable entries, exercised name search and static/animated selection, and captured two different animated texture frames. It did not read channel history or post Discord messages. That isolated test used offline loopback game identities and an in-memory environment-to-adapter test seam; it is not an authenticated production-server deployment or proof of live emoji delivery.

## Resource and compatibility bounds

Bridge messages allow 1 attachment, 256 KiB per encoded media item and 512 KiB for the complete serialized record. Packets carry at most 16 KiB chunks. Decode limits remain 1024×1024, 60 frames and 8,388,608 pixels per complete record, including emoji. There are at most 8 custom emoji, 8 concurrent server upload assemblies, 16 queued server jobs, 64 admitted game-thread packet tasks and 64 tracked upload senders. Per-player pacing is a five-message burst, then one/second, with additional packet/byte admission limits. Assemblies expire after 15 seconds. Each message conversion shares at most eight media attempts and a six-second total fetch/decode deadline; repeated emoji IDs (including failures) resolve once per static/animated identity. One bounded media worker prevents slow DNS/decoding from occupying the bridge worker indefinitely. Client ACK wait is 15 seconds; HTTP requests have bounded bodies and deadlines. Bounded queues can reject work under load; this is not a high-volume channel archive.

A server and client retain at most 12 transcript records and 16,777,216 decoded pixels including emoji. The server replay window retains 2,048 recent `(player UUID, request UUID)` keys across reconnect, not across restart. Transfer metadata cannot select files or URLs on the server. Clients upload bytes from their own confined regular-file upload directory; the server revalidates them. Media fetching allows only approved Discord HTTPS CDN paths, rejects local-address resolution and redirects, and never forwards bot authorization to CDN requests.

The network channel accepts Forge ABSENT/vanilla compatibility versions; the server avoids custom packets for peers without it and sends authorized plaintext receive fallback. Client-side composer sends fail when the server bridge is absent/disabled. Pure vanilla interoperability has not been exercised with a vanilla binary; no-channel recipients cannot upload or send through normal chat. Legacy mod protocol version mismatches are rejected rather than guessed.

## Actual validation and remaining limits

Local checks passed 49 core, 17 fake configuration/redaction, 65 loopback HTTP/wire and 36 original mock-client assertions. A real Forge dedicated server and Alice/Bob clients passed native/network assertions, plus 10 real X11 clipboard/lifecycle checks and a separate headless-caller check. These cover authoritative identity, media/emoji, spoof/replay rejection, reconnect, native chat, actual OS clipboard/F2 input, stable mentions and per-message spoiler concealment. These game tests use a labelled **server-owned TEST peer**, and HTTP contract tests use loopback official-REST fixtures.

A separate, explicitly authorized live test harness supplied the bot credential from its test environment in memory, without writing production config. It sent exactly three marked posts through the official adapter (text with one verified, approved member mention, small original PNG, small original animated GIF). It read back only their returned message IDs, verified mention policy, preserved media bytes/animation and bounded bridge-record conversion, and confirmed stable record IDs on repeated reads. It did not poll unrelated history, delete posts, alter Discord settings or establish live human-to-game receiving. Bot self-posts are intentionally excluded by normal ingress filtering. A send receipt is validated before reporting success; an invalid receipt reports uncertain delivery without automatically retrying the POST.

`verify-multiplayer.py` creates a separate ignored `run-mp/` loopback/offline test profile, strips live Discord environment settings (including the lowercase test-only variables), limits game JVM heaps/CPU and shuts down its processes. It does not change an existing server or runtime network policy. Gradle export uses the pinned ForgeGradle RunConfig token helpers because JavaExec is populated only inside its exec action. Only `MOD_CLASSES` is retained from generated run environment; arbitrary host secrets are not exported.

Still unverified: full live human Discord-to-game ingress and game-to-Discord round trip on an authenticated production server, pure vanilla binary compatibility, independent production-launcher installation and exhaustive font glyph coverage. JPEG decoding is covered by core tests; actual multiplayer media tests use PNG/GIF. Gateway/resume, message edits/deletes/reactions, threads/DMs, voice/video/stickers, WebP/APNG, guild-wide discovery/search and durable offline catch-up are not implemented. No deployment or Release is part of this work.

Native T-chat prototype: real ChatScreen/media cells and Enter-to-bridge PNG were exercised through game networking, including two different native GIF texture frames, ordinary vanilla chat without bridge duplication, and `/list` while bridge routing was selected. This does not establish compatibility with all widths/font packs/chat mods, narration, text selection or every possible attachment interruption. The native regression driver now covers controlled decode Clear/replacement/errors, Escape, immediate/repeated Enter, later drafts/files during delayed send success/rejection, captionless GIF and disconnect. PNG/GIF framebuffer checks include 100% line spacing and minimum width, plus 0.5 chat scale/50% spacing. Other font packs/chat mods/narration and full opacity/fade coverage remain unverified. Await visual review before considering the presentation final.

Native author-name selections are stable identities: Discord snowflakes become explicit `D@display` tokens and Minecraft profile UUIDs become `M@playerId` tokens. Targets must already be present in the trusted server registry; this is not a guild-wide member directory or display-name lookup. Manual lookalike strings do not create allowed mentions. Client-provided sender identity and unknown target UUIDs/IDs are rejected. Discord roles/everyone/here remain suppressed. Spoiler uploads include the conventional `SPOILER_` name and `is_spoiler` metadata; receives accept that name, `is_spoiler`, or attachment flag8 and conceal pixels locally until explicitly revealed. These REST contracts are loopback fixtures, not live Discord evidence.

### Incoming Discord author display

Minecraft native chat renders incoming Discord messages as `[D] memberDisplay: text`. The actual server formatter uses literal components: the configured guild member nickname falls back to the user's global display name, then username. Clicking the displayed author still inserts a stable-ID-bound `D@display` mention, and author hover retains the Discord identity; names and body text cannot inject component actions. Minecraft-to-Discord remains `<playerName> text`.

The server resolves only authors of new messages in the configured channel with the official single-member endpoint; it does not list members or request a new intent. Names are bounded to 64 characters, with at most four lookups and a shared two-second lookup budget per four-message polling page. A 128-entry cache refreshes after 60 seconds, with a 15-second negative cache on lookup failure. Missing, invalid, mismatched or unavailable member metadata falls back to the message's safe user display. Cache state is cleared when the adapter closes. No roles or complete member responses are retained.

`python3 scripts/verify-discord-author.py` under a 1280×900 Xvfb display drives actual Minecraft native chat using production REST conversion and server packets against a loopback peer. It verifies nickname/global/username fallback, special characters, author hover and physical click insertion, and saves original 1100×800 screenshots. This is local integration evidence, not a live human Discord message. No messages are sent by this test.

### Optional client installation

DisCraft's client installation is optional. With DisCraft installed on the server,
permitted players without the mod retain configured join/quit/death/advancement
notifications and ordinary Minecraft chat relaying. Discord ingress uses native
`[D] display: text` components for these players. Custom emoji become `:name:`;
media receives a generic client-required label, without URLs, filenames or custom
wire metadata. Safe `%item` names and vanilla item hover remain available when
`itemDisplay=true`. Clipboard uploads, image rendering, the emoji picker and
selected stable-ID mentions require the client enhancement.

The pinned Forge 47.4.0 channel uses `NetworkRegistry.acceptMissingOr("4")` on
both ends: absent endpoints are accepted; installed endpoints offering another
protocol are rejected. In this version `ABSENT` is ChannelData, so comparing a
String directly with that object does not accept an absent channel. Every server
custom-packet send checks the exact negotiated Forge protocol. The generic
`isRemotePresent` helper also accepts minecraft:register lists, which can mirror
the server channel even when the client did not negotiate it; those lists alone
do not enable DisCraft packets. Installing DisCraft on a client also
allows joining a server without DisCraft, with its enhancements inactive.
This policy does not waive client requirements of other content mods.

Ordinary native chat stays on Forge's existing chat path. DisCraft neither
cancels nor manually republishes it. A bounded observation of the native player
chat packet confirms broadcast after asynchronous Forge listeners have finished,
so a later cancellation does not leak a Discord relay. Raw signed message bodies
and original packets are forwarded unchanged; `%item` modifies only the unsigned
native presentation using a main-thread authoritative snapshot and the existing
NBT whitelist. Discord receives that snapshot's semantic name/tooltip PNG, never
the full item tag. This path shares bridge player/rate/queue limits, bounds its
pending admissions and expires them; disconnect clears peer state. An uncertain
Discord delivery is not retried. No-client fallback author hover is informational;
click-to-insert stable-ID mentions remain a client enhancement.

`python3 scripts/verify-optional-client.py` runs actual isolated Forge worlds with
an independently compiled instrumentation mod that has no DisCraft dependency.
It asserts DisCraft is absent from ModList, checks mixed enhanced/unenhanced
peers, serverless enhancement fallback and a synthetic incompatible channel.
All REST/media requests terminate at its local fake-credential receiver. These
offline controlled-world checks do not establish production online-session
cryptographic validation or compatibility with an arbitrary modpack.
